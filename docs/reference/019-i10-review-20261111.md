## Findings

### P2 — A refresh could make an already frozen upstream attempt unavailable (fixed)

Locations: apps/core/src/main/java/com/omni/platform/modules/scheduler/metadata/
OutputWorkReadiness.java:38 and OutputReadinessController.java:23;
libs/py-common/py_common/storage/output_readiness.py:read_for.

OutputWorkReadiness.read previously read output_work_ready_catalog by atomicWorkId alone;
OutputReadinessController.work had no attempt selector. That catalog points to
the latest promoted registration and removes superseded row ownership. In
PostgresMetadataReader.read_for, a worker requested only atomicWorkId and then
correctly rejected a reply whose atomicAttemptId/dataVersion differed from its
frozen approvedInputs. A concurrent refresh of the same work could therefore make
an already dispatched dependent fail, even when the original immutable Parquet
version remains available. This is an availability defect, not permission to use
the newer proof or relax lineage checks.

Evidence: the V23 catalog definition, the Java lookup, the Python identity checks
and test_worker_resolves_frozen_work_proof_instead_of_latest_partition's attempt
mismatch case. The new PostgreSQL regression and real refresh-versus-frozen-reader
E2E below cover preservation without weakening this strict rejection.

Owner-approved bounded correction: persist immutable evidence of actual VERSIONED READY
promotion, add an optional atomicAttemptId selector to the private work-proof API,
and use it for frozen worker reads. Historical registration/SUCCESS alone must not
be reinterpreted as READY. Preserve current/latest discovery and the strict legacy
route. The owner approved the V26 data-model/API amendment during this review.
V26 now adds output_work_ready_history and output_work_ready_attempt_catalog.
The existing READY transaction inserts history only for an actually current,
VERSIONED, immutable output. The history is never inferred from registrations or
SUCCESS and rejects UPDATE/DELETE. Default lookup still reads the current catalog;
the optional attempt selector and dependency binder can read retained VERSIONED
proofs. Mutable CANONICAL history remains unavailable after supersession.

Focused PostgreSQL/controller checks pass (192 cases, zero failures/skips): refresh
preserves the frozen attempt/version and physical coordinate; default discovery
advances; wrong work/attempt returns nothing; canonical refresh creates no immutable
history; an injected history-write failure rolls back registration, status, heads
and READY before a successful retry. The final worker-chain target passes 14/14,
including an actual API/Parquet read of frozen EOD/Indicators proofs after a newer
rerun advances discovery; exact original physical coordinates and versions are
asserted by the real Python reader and validated Parquet buffer.

### P2 — Query shutdown could interrupt audit after terminal commit (fixed)

Location: apps/query-service/app/manager.py:190. Deterministic regression:
apps/query-service/tests/test_manager.py:168.

QueryManager.\_run_claim awaited a DB completion in a thread and then wrote its
audit. A caller could observe the committed terminal state and call stop(), which
cancelled the worker before the await resumed and lost the audit. The full Query
gate exposed this race in test_scan_limit_fails_before_execution.

The finalization task now shields only DB completion plus audit; cancellation waits
for that task before shutdown returns. Query execution itself remains cancellable.
test_shutdown_after_terminal_commit_waits_for_its_audit uses thread barriers after
the real commit and verifies exactly one terminal audit after shutdown. This is
graceful-shutdown safety, not durable crash recovery or a new audit outbox.
