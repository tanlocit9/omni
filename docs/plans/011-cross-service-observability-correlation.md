# Cross-Service Observability Correlation Implementation Plan

Status: Proposed supporting plan; not yet assigned roadmap increment IDs
Canonical status owner: [`plans/roadmap/README.md`](../../plans/roadmap/README.md)
Scheduling rule: reconcile dependencies and add roadmap increments before implementation selection

## Goal

Introduce one consistent correlation model for HTTP requests, Kafka processing, and downstream service calls across Core, Analyzer, Ingestor, Query Service, and future Omni services.

The implementation must make one logical operation searchable across service logs without confusing transport identifiers, domain identifiers, and distributed-tracing identifiers.

This plan standardizes:

- W3C Trace Context (`traceparent` and `tracestate`) for distributed tracing;
- `X-Request-ID` for operator-facing HTTP request identification;
- Kafka headers for trace and request-context propagation;
- `executionId` and `parentExecutionId` as job-domain correlation fields;
- scoped Java MDC and Python `ContextVar` logging context;
- consistent field names and lifecycle/cleanup rules;
- structured logs suitable for later collection by Loki, OpenSearch, or another backend.

The first increment provides correlation and structured logs without requiring a tracing backend. OpenTelemetry span export is introduced only after context propagation is proven.

## Outcome

After implementation:

- every HTTP request has a validated or generated request ID returned in `X-Request-ID`;
- services accept and propagate valid W3C trace context;
- every Kafka command, status, upsert, and notification preserves trace context in Kafka headers;
- logs emitted while handling HTTP or Kafka work automatically include available correlation fields;
- asynchronous work does not leak context into unrelated requests or records;
- job logs consistently include `executionId`, `parentExecutionId`, `workType`, and `workKey` when available;
- Core, Analyzer, and Ingestor use the same names and semantics for shared fields;
- malformed or untrusted correlation headers are replaced safely and never break business processing;
- operators can begin with a request ID, trace ID, execution ID, or Kafka coordinate and follow the operation across services;
- a later OpenTelemetry collector/exporter can be enabled without redesigning application contracts.

## Non-Goals

- Do not replace `executionId` with `traceId`; they have different lifetimes and semantics.
- Do not use Kafka's internal protocol correlation ID as an application correlation ID.
- Do not put trace or request IDs into Kafka payload business schemas unless a separate durable audit requirement is approved.
- Do not require a production observability vendor or backend in the first increment.
- Do not log payload bodies, authorization values, Telegram tokens, cookies, or other secrets.
- Do not make telemetry export availability a prerequisite for serving requests or processing Kafka records.
- Do not add analytical data, PostgreSQL tables, or Redis state for correlation.

## Current-State Findings

- Core's log pattern references MDC `traceId`, but no application tracing dependency or MDC population was found, so it normally renders `system`.
- No shared application support exists for `correlationId`, `X-Correlation-ID`, `X-Request-ID`, `traceparent`, or `tracestate`.
- Python ASGI applications configure ordinary logging but have no request-context middleware or `ContextVar`-backed log enrichment.
- Kafka publishers send keys and payloads without application trace headers.
- Kafka consumers log topic, partition, offset, and key, but do not install correlation context while processing a record.
- The manual-job `requestId` is a domain/audit identifier, not a general HTTP request ID.
- The `requestId` generated by Core's global exception handler is created only after failure and is not linked to preceding logs.
- Job messages already carry useful domain identifiers: `jobDefinitionId`, `executionId`, `parentExecutionId`, `workType`, and `workKey`.

## Correlation Model

### Identifier Semantics

| Field                            | Source                                          | Lifetime                                      | Propagation              | Purpose                                             |
| -------------------------------- | ----------------------------------------------- | --------------------------------------------- | ------------------------ | --------------------------------------------------- |
| `traceId`                        | W3C trace context/OpenTelemetry                 | Distributed operation                         | HTTP and Kafka headers   | Connect spans and logs across services              |
| `spanId`                         | OpenTelemetry                                   | One operation segment                         | Derived from active span | Distinguish service/operation segments              |
| `requestId`                      | Incoming valid `X-Request-ID` or generated UUID | HTTP request and resulting asynchronous chain | HTTP and Kafka headers   | Operator-facing lookup and support reference        |
| `executionId`                    | Scheduler/job domain                            | One job work execution                        | Existing message payload | Correlate durable job state and processing          |
| `parentExecutionId`              | Scheduler/job domain                            | Fan-out job aggregate                         | Existing message payload | Correlate sibling work and aggregate completion     |
| `jobDefinitionId`                | Scheduler/job domain                            | Job definition                                | Existing message payload | Identify the configured job                         |
| `workType` / `workKey`           | Scheduler/job domain                            | Work item                                     | Existing message payload | Identify the exact logical partition/work item      |
| `topic` / `partition` / `offset` | Kafka consumer                                  | One consumed record                           | Log context only         | Locate/replay the transport record                  |
| `messageKey`                     | Kafka producer/consumer                         | Kafka message                                 | Kafka record key         | Relate transport records where key semantics permit |

`requestId`, `traceId`, and `executionId` must remain separate log fields. The implementation must not alias one to another.

### Canonical Names

Use these exact case-sensitive structured-log field names:

```text
service
environment
traceId
spanId
requestId
executionId
parentExecutionId
jobDefinitionId
workType
workKey
topic
partition
offset
messageKey
httpMethod
httpPath
httpStatus
```

Use these wire names:

```text
HTTP:
  traceparent
  tracestate
  baggage                 # allowlisted use only
  X-Request-ID

Kafka headers:
  traceparent
  tracestate
  x-request-id
```

Kafka header names are lowercase ASCII. Consumers may temporarily accept case variants during migration, but producers emit only the canonical names.

### Validation Rules

- `traceparent` must be parsed by standards-compliant OpenTelemetry/W3C libraries; never parse it with handwritten substring logic.
- Invalid trace context starts a new trace and records a rate-limited warning without echoing the raw value.
- `X-Request-ID` accepts visible ASCII identifiers of 1-128 characters matching `[A-Za-z0-9._:-]+`.
- Missing or invalid request IDs are replaced with a UUID string generated by the receiving HTTP service.
- Kafka consumers generate a request ID only when no valid propagated value exists. This supports events created outside HTTP flows.
- Incoming correlation fields are diagnostic metadata, never authorization or idempotency evidence.
- Baggage is disabled by default. If enabled later, only explicitly allowlisted keys may propagate.

## Contract Impact

### Kafka/service-to-service protobuf

No protobuf payload field is required for trace or request context. Kafka headers carry propagation metadata independently of JSON/protobuf payload evolution.

Existing domain fields (`executionId`, `parentExecutionId`, `jobDefinitionId`, `workType`, and `workKey`) remain in canonical job contracts. Producer and consumer adapters must continue preserving them.

If a future non-Kafka transport cannot carry metadata headers, define a transport envelope through a separate contract change rather than adding tracing fields independently to every business message.

### Object-storage JSON manifest

No schema change. Existing `sourceExecutionId` lineage remains a domain/audit reference, not a trace ID.

### Storage path/dataset ownership

No change.

### Public Java/Python API

New shared observability APIs are introduced:

- Java utilities/interceptors for context extraction, scoped MDC enrichment, and Kafka header injection;
- Python `py_common.observability` APIs for context storage, logging enrichment, ASGI middleware, and Kafka extraction/injection.

Keep these APIs small and transport-focused. Business modules should provide domain fields but should not manipulate global logging internals directly.

### Configuration/environment contract

Add shared configuration with safe defaults:

```text
OBSERVABILITY_SERVICE_NAME=<service name>
OBSERVABILITY_ENVIRONMENT=<environment>
OBSERVABILITY_LOG_FORMAT=json|console
OBSERVABILITY_TRACING_ENABLED=false
OTEL_EXPORTER_OTLP_ENDPOINT=<optional>
OTEL_TRACES_SAMPLER=parentbased_traceidratio
OTEL_TRACES_SAMPLER_ARG=<environment-specific ratio>
```

`OBSERVABILITY_TRACING_ENABLED=false` disables span export, not request-ID generation, context propagation, or log enrichment.

## Architecture

### Shared Context Lifecycle

```text
HTTP ingress or Kafka consume
  -> validate/extract transport context
  -> create/continue trace context
  -> install request + domain + transport fields in scoped context
  -> execute application handler
  -> inject current context into outbound HTTP/Kafka calls
  -> emit completion/error log
  -> always clear/reset scoped context
```

Context cleanup is mandatory in `finally`/scope-close paths. Thread pools, async tasks, retries, and sequential Kafka records must not inherit stale fields.

### Java Direction

Use supported Spring Boot/Micrometer Tracing and OpenTelemetry propagation integration rather than a custom trace implementation.

- Micrometer Observation/Tracing owns active trace/span context.
- A `OncePerRequestFilter` owns `X-Request-ID` validation/generation and HTTP MDC fields.
- Spring Kafka producer/consumer interceptors or record/message interceptors own trace header propagation.
- A small `AutoCloseable` MDC scope owns job-domain and Kafka-coordinate fields.
- Logback emits structured JSON in deployed environments and readable console output locally.
- The global exception handler reads the active request ID rather than generating an unrelated error-only ID.

### Python Direction

Create `libs/py-common/py_common/observability/` as the shared implementation.

Suggested modules:

```text
context.py       # ContextVar values and token-based reset scopes
logging.py       # LogRecord filter/formatter and redaction policy
http.py          # ASGI middleware and outbound HTTP helpers/hooks
kafka.py         # aiokafka header extraction/injection helpers
tracing.py       # OpenTelemetry setup behind configuration
```

- `ContextVar` stores diagnostic fields for async-safe logging.
- ASGI middleware validates/generates request IDs, extracts W3C context, and returns `X-Request-ID`.
- Kafka helpers extract headers before payload decoding and reset context after each record.
- Shared producer wrappers inject current context without forcing each call site to build headers manually.
- Logging defaults remain functional when OpenTelemetry packages/export are disabled.

## Outbox and Asynchronous Boundary Decision

The scheduler outbox is a durable boundary. Capturing only the active thread's trace context at dispatch time would create a new unrelated trace after delay/retry. Therefore, Increment 3 must persist an allowlisted observability-header snapshot with each outbox message.

Rules:

- store only `traceparent`, optional `tracestate`, and `x-request-id`;
- enforce per-value and aggregate size limits;
- never persist arbitrary Kafka or HTTP headers;
- treat stored values as diagnostic metadata;
- preserve the same stored context across retries;
- do not mutate an outbox row's trace context after creation;
- existing rows with no headers remain publishable and create a new producer context.

## Security, Privacy, and Reliability

- Correlation values are untrusted input and must be length/character validated.
- Raw invalid headers must not be copied into logs or error responses.
- Do not place user names, emails, tokens, query text, symbols lists, or payload bodies in baggage.
- Apply log redaction to authorization, cookies, API keys, Telegram credentials, and configured secrets.
- Normalize HTTP route templates for log fields when available; avoid unbounded raw URL cardinality.
- Trace/log enrichment must fail open: observability failures must not fail business processing.
- Rate-limit warnings for malformed headers and exporter failures.
- Context must be cleared in `finally`, including cancellation and exception paths.
- Ensure scheduled background tasks begin with a clean context unless explicitly linked.

## Rollout Strategy

Use a backward-compatible, consumer-first rollout:

```text
1. deploy shared logging/context support with propagation disabled
2. deploy HTTP extraction and response request IDs
3. deploy Kafka consumers that accept optional headers
4. deploy worker producers that emit headers
5. deploy Core/outbox producers that persist and emit headers
6. verify propagation metrics and cross-service searches
7. enable optional span export at low sampling
8. increase sampling only after capacity review
```

No topic migration is required. Header-absent records remain valid throughout rollout.

### Rollback

- Disable span export through configuration without disabling correlation logging.
- Producer header injection can be disabled independently if an interoperability issue occurs.
- Consumers must continue accepting both header-present and header-absent records.
- Do not roll back the outbox database column after deployment; leave it nullable and unused if necessary.
- Structured JSON logging can fall back to console formatting through configuration.

## Risks and Mitigations

| Risk                                       | Impact                                       | Mitigation                                                                          |
| ------------------------------------------ | -------------------------------------------- | ----------------------------------------------------------------------------------- |
| Context leaks across worker tasks          | Unrelated operations appear connected        | Scope/token reset in `finally`; concurrency and sequential-record tests             |
| Custom propagation diverges from standards | Broken traces across libraries/services      | Use OpenTelemetry W3C propagators; handwrite only request-ID validation             |
| Outbox loses originating context           | Delayed messages create disconnected traces  | Persist allowlisted headers at outbox creation and reuse on retry                   |
| Header spoofing                            | Misleading support/audit searches            | Validate lengths/characters; treat identifiers as non-authoritative                 |
| High-cardinality metrics                   | Monitoring cost/performance degradation      | Keep IDs in logs/traces only, never metric labels                                   |
| Excess trace volume                        | Collector/storage overload                   | Parent-based sampling and staged enablement                                         |
| Exporter outage affects service            | Business processing degradation              | Batch/non-blocking export, bounded queues, fail-open behavior                       |
| Mixed deployment versions                  | Missing links during rollout                 | Optional headers, consumer-first deployment, propagation coverage metrics           |
| `requestId` naming confusion               | Manual trigger audit ID mistaken for HTTP ID | Document semantics; keep structured HTTP context independent from domain DTO fields |
| Log format breaks local workflows          | Reduced developer usability                  | Configurable JSON/console formats with stable canonical fields                      |
