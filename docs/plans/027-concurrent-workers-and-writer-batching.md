# Plan 027 — Single-Instance Concurrent Workers and Writer Batching

Status: Supporting implementation plan. Canonical schedule and statuses belong to [Phase 12](../../plans/roadmap/phase-12-worker-throughput-and-writer-batching.md) and the [increment registry](../../plans/roadmap/implementation-increments.md). Implementation starts only after P11-I5 is completed. This plan does not claim runtime changes.

## Goal

Drain the large daily/EOD Kafka fan-out with bounded concurrent processing while keeping command offsets, per-child terminal status, MinIO writes, parent aggregation, and signal notifications correct. Share the Python writer interface across eligible producers without making the parent execution ID a write lock.

## Outcome

One Ingestor instance, one Analyzer instance, and **one independent Python writer service instance** support explicitly configured, bounded in-flight work. Analyzer computes signal candidates concurrently and hands compatible results to a dedicated Kafka write-intent topic. The writer service uses shared `py-common` Kafka, status, and storage abstractions, buffers by logical `writeKey`, applies ordered transitions to one in-memory history snapshot, and performs a bounded physical write batch. Each child receives its own authoritative status after output succeeds. Kafka is the durable handoff; the writer's bounded in-memory batch is working state, not another persistent queue. Redis is unnecessary while writer replicas remain at one.

## Eligibility and implementation increments

- **P12-I1 — offset safety and baseline:** After P11-I5, measure complete representative cohorts by topic/group/job type and stage (provider, compute, lock wait, storage, status, Platform aggregation). Explicitly disable auto-commit on affected Python command consumers. Commit only the contiguous completed prefix per Kafka partition after successful output and terminal-status publication. Define processing failure, status-publish failure, retry/backoff, shutdown, and rebalance behavior before allowing parallel work.
- **P12-I2 — policy and independent-output concurrency:** Implement a code-owned job-type policy with `writeMode` (`SINGLE` or `BATCH`), a logical `writeKey` resolver, compatible operation type, and safe concurrency defaults. Keep dependency eligibility separate from writer ownership and retain mutable job parameters in `configJson`. Snapshot resolved routing fields in command payloads via coordinated Java producer/Python consumer updates. Introduce bounded per-service/per-job admission and explicit provider/storage budgets; pilot only jobs with independent output objects. Default concurrency to one until an override is measured and verified.
- **P12-I3 — Platform bulk status application:** Keep the existing one-status-per-child Kafka payload. Make `JobStatusConsumer` consume bounded batches of records and add `JobService.applyStatuses` that validates each child against persisted execution/work identity, applies changed child rows, groups by persisted parent ID, then locks and aggregates each affected parent once per batch. Sort parent lock acquisition deterministically; preserve duplicate/invalid status behavior, exactly one parent terminal transition and notification, and standalone execution handling. Commit/ack only after all relevant database transactions succeed. If a subset fails, replay the unacknowledged records safely via terminal idempotency, identify and report the failing record, and isolate malformed records from valid work for processing without silently acknowledging them. Without a durable quarantine handoff, pause the affected partition and alert an operator; never commit past the failing offset, while unrelated partitions may continue. Valid rows already applied must remain idempotent on replay. A durable DLT envelope, retention, replay authorization, and repository-wide poison-record policy are deferred to [technical debt 010](../technical-debt/010-kafka-poison-record-and-dead-letter-policy.md) and are not a P12-I3 completion gate. Benchmark database write count, parent-lock time, status lag and notification equivalence against the single-record path.
- **P12-I4 — independent Python signal writer service:** Add a separate Nx service (proposed `apps/dataset-writer`) using shared `py-common` Kafka/status/MinIO abstractions. Analyzer emits an immutable, validated signal write intent to a new Kafka topic keyed by logical `strategy + timeframe + exchange`; writer consumes the topic in one group and is the only mutator of that signal history/current projection. `SYNC_SIGNALS` submits a computed candidate, while `EVALUATE_SIGNALS` submits a typed evaluation operation that the writer executes under the same key; only mutually compatible upserts share one physical write batch. Apply transitions against the evolving in-memory snapshot in queue order so `previousSignal`, `signalChanged`, revision, `newSignalDate`, current projection and notifications keep their current semantics. If that cannot be proved, retain single-operation writes for affected signal paths until resolved. Flush on count, wait time or bounded-memory pressure based on baseline evidence.

The write-intent topic is a durable transport boundary, not a second database. The writer still publishes individual child status records; Platform batches their consumption and database application, so the status wire payload remains unchanged. The Analyzer command offset may advance only after Kafka acknowledges the validated intent; if compute fails before intent publication, publish its authoritative failure status before committing. If source Kafka and intent Kafka are one cluster, evaluate a transactional consume-produce offset handoff; otherwise use at-least-once with deterministic intent identity and idempotent replay. The writer holds its own intent offsets until MinIO publication and per-child terminal-status publication complete. Its RAM buffer is disposable after restart.

## Processing and commit contract

1. Decode a source command with `executionId`, `parentExecutionId`, work identity, resolved routing and Phase 11 correlation headers. For `BATCH` output, emit a versioned, validated write intent carrying logical dataset/partition identity, operation, deterministic `intentId`, candidate/reference, execution identity and diagnostic headers. Derive `intentId` from immutable operation identity such as `executionId + operation + logical row/output identity + schema/model version`; the exact canonical serialization and hash/version belong to the write-intent contract. Preserve `correlationId` and `requestId` only as diagnostic traceability values: they must never become ownership, idempotency or deduplication keys. Do not put physical MinIO paths into business payloads. Writer derives the canonical path and rejects unsupported mode/key/operation combinations.
2. Analyzer admits compute only within bounded global/job limits; writer admits intents within its own storage and per-key limits. A physical batch may contain children from different parents; it cannot combine incompatible operations or unrelated logical outputs. Both `SYNC_SIGNALS` and `EVALUATE_SIGNALS` for one history key must pass through the same writer service.
3. Track two offset boundaries: source command is safe after an acknowledged durable intent (or a completed error status), while writer intent is safe only after its MinIO outputs and terminal status publication. Keep per-record topic/partition/offset and execution identity through both boundaries; commit only a contiguous completed prefix per partition. Apply deterministic idempotent upserts to survive duplicate intent publication and writer replay. If storage succeeds but status publication fails, do not mark the intent complete.
4. Publish status per child only after all outputs belonging to that child have been validated and written. Preserve Platform's authoritative parent aggregation and avoid publishing a parent terminal status from the writer.
5. On both consumers, commit only the contiguous completed offset prefix for each partition. Pause admission under backpressure; on shutdown or partition revocation stop admission and drain within a bounded deadline, otherwise leave unfinished offsets uncommitted. Acknowledgment of an in-memory batch never commits a writer intent.
6. P12-I3 addresses the known full-child scan and parent lock per status: batch records by persisted parent, update children and aggregate once for that parent, preserving transaction and notification semantics. Measure lock wait, status lag and any remaining bottleneck.

The implementation must account for Kafka keys that currently identify a symbol while signal history is keyed by strategy/timeframe/exchange. Same-key routing on an existing topic alone does not serialize writers across different topics. V1 enforces shared-object serialization inside one dataset-writer process; increasing writer replicas is outside this plan.

## Job policy pilot matrix

| Job family                                                               | V1 policy                                           | Concurrency boundary                                                                         |
| ------------------------------------------------------------------------ | --------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Stock price EOD, intraday EOD, indicators, symbol features               | `SINGLE` write per command                          | Different logical objects may run concurrently; one writer per object, provider limits apply |
| Signal calculation                                                       | `BATCH` for compatible history upserts after P12-I4 | Concurrent compute, one ordered writer per shared history key                                |
| Signal outcome evaluation                                                | `SINGLE` operation through signal writer            | Serialize against signal upserts on the same history key                                     |

All throughput and batch sizes are deployment overrides, not fixed numerical promises. Review the exact producer/handler/path mapping before finalizing the registry.

## Dataset Outputs

No new analytical dataset output. Existing EOD, feature, signal history/current-signal, Sector Wave, and Sector Transition path ownership remains authoritative. For the signal history/current-signal paths, ownership of physical writes moves from Analyzer handlers to the dataset-writer service. Signal batching must preserve row identity, Parquet schema, existing read-back validation, immutable publication where used, and READY-last behavior. Physical bucket/path values are derived by the owning storage layer, not carried as business routing fields in Kafka.

## Metadata Outputs

No dataset metadata output. Preserve current manifests, `dataVersion`, lineage, and readiness semantics. A child is not terminal-successful merely because its result entered a batch.

## Algorithm Feature Outputs

No direct algorithm feature output.

## Algorithms Unlocked

No new algorithm. Existing daily/EOD, signal, sector and outcome work gains bounded throughput without changing analytical decisions.

## Out of scope and High Availability notes

No Redis lease, distributed lock, multiple Analyzer/Ingestor/writer replicas, cross-instance write ownership, dedicated Rust writer, provider-rate-limit bypass, historical command replay, or ad hoc rewrites of `RUNNING` rows. The [High Availability Notes](../deployment/003-high-availability-notes.md) define the separate multi-instance promotion gate, including stale-writer protection after rebalance.

## Acceptance Criteria

- P12-I1 establishes baseline and proves no affected command offset advances before output and terminal status, or an explicitly durable handoff.
- P12-I2 demonstrates bounded concurrent progress for different objects without concurrent writers to one object, with provider/storage budgets enforced.
- P12-I3 applies bounded groups of individual status records with at most one parent aggregation per affected parent per group, preserves standalone statuses, isolates and reports bad records explicitly, and acknowledges only after durable database application. Duplicate/replayed records do not duplicate terminal notifications. A repository-wide DLT/replay platform is not required for completion.
- P12-I4 runs the independent Python dataset-writer as the only selected signal-history mutator and shows fewer physical writes for eligible shared-history cohorts while preserving exact decisions, projections, statuses and notifications. No child reports success on handoff or before physical write.
- Restart, rebalance, replay and shutdown tests preserve data and complete or replay unfinished work; no unbounded buffer or task creation occurs.
- Before/after evidence is comparable by job mix and reports Kafka lag, terminal throughput, p50/p95/p99 stage durations, failures, writer contention, MinIO/CPU/memory use and parent aggregation latency.
- All canonical contract/flow/data docs, repository guidance and CI evidence are synchronized before marking an increment complete.
